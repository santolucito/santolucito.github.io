The problem

End users can show the task, not code it

Spreadsheet help forums are full of requests for one-off string reformatting: names, dates, phone numbers, addresses.

The person asking can give examples of what they want, but not a formula or a script.

Goal: learn the transformation from a few examples, fast enough to feel instant.

The one idea to remember

Don't pick a program. Keep all of them, then intersect.

A version-space algebra over a string DSL: exponentially many consistent programs, stored in a polynomial-size DAG. Each new example is an intersection. Ranking picks one at the end.

This is the slide to remember. Classical enumerative synthesis searches for one program and checks it. FlashFill builds a data structure that denotes the set of all programs consistent with an example, and it does this without enumerating them. More examples mean intersecting these sets. Choosing among the survivors is a separate step: ranking. The term "version space" comes from Mitchell's concept learning, and Lau et al. applied it to programming by demonstration.

The language

A small DSL built for string edits

P := Switch((b1,e1), …, (bn,en))

e := Concatenate(f1, …, fn)

f := ConstStr(s)

   | SubStr(vi, p1, p2)

   | Loop(λw. e)

p := CPos(k) | Pos(r1, r2, c)

r := TokenSeq(T1, …, Tm)

b := ∨ of ∧ of Match(vi, r, k)

A program is a concatenation

Constant strings and substrings of the inputs, glued together.

Substrings are cut at positions

A fixed index CPos(k), or a context Pos(r1, r2, c). Regexes are just sequences of tokens.

Conditionals and loops on top

Switch chooses a trace by Match predicates. Loop repeats one for w = 1, 2, …

5

The DSL is where most of the design effort went. It's expressive enough for the forum tasks and restricted enough that the set of consistent programs has a compact representation. The integer c inside Pos can be k or k1·w + k2, and that is how Loop's variable w reaches positions. Tokens are character classes such as AlphaTok, NumTok, UpperTok, LowerTok, WhiteSpaceTok, StartTok and EndTok, plus special characters. Negative k or c counts from the end.

A position is a gap between characters, numbered from 0 up to the string's length.

SubStr(v1, p1, p2) copies whatever lies between two positions of input v1.

The simplest position is a number: CPos(5) means “gap 5”. It fits the first example, then cuts the second name mid-word.

What we mean is “the gap right after the space, where the letters start”. The next slide shows how to write that down.

Build this up slowly: students have not seen the DSL in action yet. SubStr takes an input and two positions and copies the text between them. Positions are gaps, not characters: "Alan Turing" has 11 characters and 12 gaps, numbered 0 to 11. The obvious way to name a gap is by its number. CPos(k) does that, and a negative k counts from the end, so CPos(-1) is always the end of the string. Gap 5 works for Alan Turing because "Alan" has four letters, but Ada is three letters, so gap 5 lands inside "Lovelace". The name is a stand-in: a fixed index bakes the length of the first name into the program. Ask the class what rule a person would use; they'll say "after the space". That is what Pos captures.

This is the construct that makes FlashFill generalize, so take your time. Tokens are character classes: AlphaTok matches one or more letters, NumTok one or more digits, and so on, with a special token for each punctuation character plus StartTok and EndTok. r1 and r2 are short sequences of tokens, and the empty sequence ε matches anything, for when one side doesn't matter. Pos(r1, r2, c) picks the c-th gap t where r1 matches some text ending at t and r2 matches some text starting at t. Negative c counts from the end. Walk the class through the grid: which gaps have whitespace on the left and letters on the right? Gaps 6 and 15. So c = 1 and c = -1 are different programs that agree on every two-word name. That sets up the ambiguity the version space has to keep, and that the ranking or another example has to resolve.

Version spaces

Keep the choices, not the programs

A version space is the set of all programs consistent with the examples so far. After one example it is enormous: too big to list, let alone test one by one. FlashFill's trick is to store it as independent choices.

Real sets are far bigger, and the saving compounds at every level: token sets inside positions, positions inside substrings, substrings inside the concatenation. The algebra is the set of operations on these factored sets: intersect them, count them and run them, all without listing programs.

8

This is the conceptual pivot of the talk. The term comes from Tom Mitchell's "Generalization as search" (1982): in concept learning you keep the set of all hypotheses consistent with the data and shrink it as examples arrive. Lau, Domingos and Weld (ICML 2000) turned it into an algebra: build the version space of a complex function by composing the version spaces of its parts. FlashFill lifts that to programming by example. The picture: take just the "Turing" piece of the output. Using what we saw on the positions slides, there are several ways to say where it starts and several ways to say where it ends. Any start can pair with any end, so 3 × 3 = 9 SubStr programs. But you don't store 9 programs; you store the two lists of 3. That's the whole idea in miniature: a product of choices stored as a sum. The same factoring happens inside each Pos (sets of r1, r2 and c) and across the pieces of the output, which is the next slide. These three-item lists are illustrative; the real sets are larger.

9

This slide answers "where did the DAG come from?" The output is built by Concatenate, gluing pieces, but the synthesizer doesn't know how the user's output was cut into pieces. Maybe "Turing, A." is one constant string; maybe it's four pieces. Trying every split separately would be exponential: a 10-character output has 2^9 = 512 ways to cut it. The paper's key observation (Section 4.3) is that there are only quadratically many pieces, one per substring: 55 here. So make a node for each cut point and an edge for each piece. Then every split is a path, and the 512 splits share just 55 edges. It's "directed" because edges go left to right, and "acyclic" because you can never return to an earlier position. For readability I've drawn only the cut points at word boundaries: 5 nodes and 8 paths instead of 11 nodes and 512.

Version-space algebra: the operations

Lift the DSL from programs to sets of programs

A set of programs, and what it means

SubStr(vi, P, P') means
  every SubStr(vi, p, p'), p∈P, p'∈P'
Pos(R1, R2, C) means
  every Pos(r1, r2, c), r1∈R1, r2∈R2, c∈C

  every Concatenate(f1, …, fn) along a
  path s→t, with each fi ∈ W(edge i)

Intersect, rule by rule

SubStr(vi,P1,P2) ∩ SubStr(vi,P1',P2')
  = SubStr(vi, P1∩P1', P2∩P2')
Pos(R1,R2,C) ∩ Pos(R1',R2',C')
  = Pos(R1∩R1', R2∩R2', C∩C')

anything else = ∅

Two more operations work on the sets directly: Size counts the programs without listing them (next slide), and Evaluate runs all of them on a new input, highlighting any cell where they disagree.

So a new example costs one intersection over these sets. FlashFill never enumerates programs, not even to check them.

This is the technical heart of the paper. A version space is the set of all hypotheses consistent with the examples seen so far, an idea from Mitchell's "Generalization as search" (1982). Lau, Domingos and Weld (ICML 2000) made it an algebra: build version spaces for complex functions by composing version spaces for their parts. In its own words, FlashFill shows "how the concepts of version-space algebra can be lifted to the PBE setting." Left card: the DSL is re-read so that every constructor takes sets of arguments, and a set-expression means every program you get by choosing one element from each set. Right card: intersection works structurally, constructor by constructor, and never lists programs. DAGs intersect like automata: nodes become pairs, and each edge label is the intersection of the two label sets. I've simplified the notation; the paper also has rules for Loop, CPos and TokenSeq (all pointwise), and Intersect returns ∅ when the constructors don't match. The paper compares the structure to BDDs, which represent huge sets of states succinctly and operate on them directly. (Source: Figures 3 and 4, and Section 5.1 for evaluation.)

12

Walk the table top to bottom; each row builds on the one above. Row 1: the "Turing" piece. As on slide 8, there are 3 ways to say where it starts and 3 ways to say where it ends, plus the option of just typing the constant "Turing". FlashFill stores those 7 things. Any start can pair with any end, so they stand for 3 × 3 = 9 SubStr programs, plus the constant: 10. Row 2: one way of splitting the output, "Turing" + ", " + "A" + ".". Each piece gets its own set. The comma-space and the period don't appear in the input, so they can only be constants: 1 option each. "A" works like "Turing": 10 options. Storage adds up to 16 entries, but the programs multiply: 10 × 1 × 10 × 1 = 100, because you choose independently for each piece. Row 3: every split at once. That's the DAG from slides 9 and 10: 55 edges, each with its own set, and 512 paths through them. The paths share edges, so storage is just the 55 sets, while the number of programs is the sum over all paths of that path's product. The punchline: the Size function (Fig. 5 in the paper) computes this count directly from the stored sets, multiplying along paths and adding across them with dynamic programming, and intersection and evaluation also work on the stored sets. The 3-per-list numbers are illustrative; real sets are larger, which only makes the gap bigger. Section 4.2 adds one more saving: tokens that match exactly the same places in the input are merged into one, so the sets stay small to begin with (the paper's example lists several ways to extract "706" from "425-706-7709").

When the intersection is empty: Switch and Loop

Adjacent DAG pieces that are the same expression, differing only in an integer, get unified. That integer becomes the loop variable w.

14

If no single trace fits every example, FlashFill partitions the examples. The partition step prefers merges that leave larger intersections, which pushes toward fewer cases. It then learns a boolean classifier over Match predicates to route new inputs to a case. SubStr2(v, r, c) is the paper's shorthand for the c-th occurrence of regex r. Loops apply the same unification idea to the DAG itself. The two examples on this slide are mine, not the paper's.

Section 5.3 defines a partial order on expressions, justified by Occam's razor. The paper admits that "some of these choices are subjective, but have been observed to work well," and it floats personalizing the order to the user. The Generate procedures use this order to return an ordered set of solutions. Ranking is where the prior lives: the version space says what is possible, and the ranking says what is likely. Later PROSE work learns it. The interaction loop at the bottom matches Section 6.1. When several outputs are possible, the tool fills in the top one but highlights the cell, and it shows "??" when no program fits. Any fix re-runs learning with the extra example.

All numbers are from Section 6.2 of the paper. The prototype was an Excel 2010 add-in called QuickCode, written in under 5,000 lines of C#, and the timings were taken on a Core 2 Duo at 2.8 GHz. The tool typically needs just one round when the user starts with one example per input format, which is usually 1 to 3 examples. The success claim is phrased relative to the DSL: nothing expressible failed to converge. That's an informal completeness claim, not a measured success rate. Note for the Critic: the benchmarks were collected by the author, and there's no baseline, user study or held-out set. It's an existence proof more than a controlled study, and forum questions may not represent what spreadsheet users actually do.

Champion · the case for a best paper award

Why this paper matters beyond its benchmark

It proved synthesis can ship

Within two years it was Flash Fill in Excel 2013: program synthesis behind a single keystroke, used by people who have never written code.

It is a recipe, not a trick

Sets of programs, intersection and ranking work for any DSL. FlashMeta/PROSE (2015) turned exactly this into a framework for building synthesizers.

What I'd build on it

Keep the version space for its guarantees, but learn the ranking and the noise handling from data. That is the gap RobustFill and later neurosymbolic work go after.

Conceded up front: the DSL and ranking are hand-engineered

It only generalizes as far as its designer anticipated, and every failure in Section 6.2 is outside the DSL. That doesn't sink it: the contribution is the algorithm (represent, intersect, rank), and PROSE showed that algorithm transfers to other DSLs.

FlashFill · Gulwani, POPL 2011

17

The Champion argues for a best paper award, specific rather than enthusiastic, and concedes the biggest weakness first. The three cards: impact (Excel 2013), generality (the version-space algebra became FlashMeta/PROSE, Polozov and Gulwani, OOPSLA 2015), and what comes next (learned ranking and noise tolerance, which is RobustFill's opening). The concession: the DSL and ranking are hand-built, and the paper's own failures are semantic tasks outside the DSL, such as date to day of week (Section 6.2). The defence: the reusable contribution is the algorithmic recipe, not the particular string DSL.

The Critic's slide: attack the claims, not the authors, and close with one experiment. As the author, my answer to the first two: the DSL and ranking are the contribution. They encode what a spreadsheet user means. The third point is real. Section 5.2 does handle noise a little: when no boolean classifier separates the partitions, it drops a singleton partition, treats that example as a typo, and asks the user (the "Kimberley" example). But that's one heuristic for one bad example, and it's the right place to hand over to RobustFill.

Discussion

What would we have to believe?

1

FlashFill generalizes from one or two examples. Is that reasoning, or is the DSL's prior doing all the work?

2

RobustFill learns the search instead. What does a neural model gain over a version space, and what does it give up?

3

An LLM can handle most of these tasks today. Which part of FlashFill's contribution still matters?

These tie back to Week 1's prediction-versus-reasoning framing and to Chollet's measure of intelligence: generalizing from few examples with a strong prior. For question 3, push on guarantees: FlashFill's output is always consistent with the examples and is an inspectable program. An LLM's answer is neither by default.
